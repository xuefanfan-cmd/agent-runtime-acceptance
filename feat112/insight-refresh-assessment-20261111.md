# D1 洞察的实践检验（FEAT-112）

日期：2026-11-12。口径：用实践检验 D1 的方法论论断——哪些偏乐观、哪些当前做不到、哪些有逻辑错误，结论落在方法论层面。实践只作判断依据，不作为页面内容。

> 2026-11-12 生成的 `D1-契约基线治理-章节稿v3.1.pptx`、`v3.2.pptx`（脚本 v0.9、v0.10）按“把实践细节写进页面”的错误思路修改，已作废，不作为后续修订基础。修订以 v3.0（脚本 v0.8）为起点。

## 一、有逻辑错误的论断

### 1. L2“测试范围由载体担保”：让被测对象裁定自己的验收范围

- **论断**：载体声明决定测什么；三条守恒“声明=绝对 / 不声明=不适用 / 声明不实=判据自动失败”给假阴性结构性防线。
- **问题**：对契约规定为 MUST 的能力，“不声明=不适用”恰恰是一个假阴性入口——实现方只要不声明，就把自己的验收义务缩小了。这与 L2 自称要堵的方向相反。载体声明只对契约本身定义为“可选”的能力成立（如 A2A 的 push 等可选能力）；平台特性几乎全是 MUST，测试范围应由契约决定，不由载体决定。
- **衍生错误**：UNSUPPORTED 被定义为“能力未声明”，把“没声明”和“声明不支持”混为一谈；§8c 要求“对每个 key 显式表态”，会破坏“键缺席时的默认行为”这类必须验证的场景。原稿 L2 样例还把 `cancelTask`、`input_required` 列为 A2A 能力位——A2A 的 AgentCapabilities 只有 streaming / pushNotifications / extendedAgentCard / extensions，CancelTask 是核心方法、input-required 是任务状态，把必选行为做成可关的能力位，正是本条错误的样例。
- **实践依据**：FEAT-112 全部 65 个场景都是 MUST，L2 在这里无可用之处；照搬后 testplan 把配置键当能力清单，把“未声明项”当合法 skip。
- **修正方向**：L2 降为“可选能力的范围圈定机制”，不作为五层栈的通用一层；明确“范围由契约决定，声明只能收窄契约允许收窄的部分”；声明 ≠ 激活，需要独立的激活证据。

### 2. 契约权威不清：testplan 被称为“契约”，L2 设计被列为预期依据

- **论断**：testplan 是四方共同输入契约；testplan 作者依据特性档和 L2 设计抽取子特性。
- **问题**：两个来源不一致时谁说了算，方法论没有回答。把 testplan 叫“契约”、把 L2（实现设计）列为依据，会让预期向实现漂移——实现怎么做，testplan 就怎么写，偏差被判成 PASS。
- **实践依据**：多条预期照实现写，或要求公开响应暴露内部字段，靠人工评审才纠正。
- **修正方向**：特性档是唯一的预期来源；L2 只用于理解实现和登记已知差距；testplan 是派生的测试设计，不是契约。补“分歧处置”：契约与实现不一致时先登记，契约正式修订后测试才跟随，不允许测试先向实现靠拢。

### 3. 五层栈的所有检查都是结构性的，没有一层检验“测试本身对不对”

- **论断**：L1 语言化 + L5 round-trip/三件绑死 + L3 判据自证，保证“测得对”。
- **问题**：这些机制检验的都是结构——格式可解析、ID 一一对应、判据对构造的样本能红能绿。有两类决定结论真假的问题它们全部看不到：
  - **预期是否忠于契约**：预期写错时，结构检查全绿；
  - **场景是否真的被激活**：前置空转时（故障没从声明的注入点进来、目标路径根本走不到），测试照样可以“通过”或“失败”。
- **实践依据**：本轮真正的问题几乎都属于这两类，没有一个是被结构检查拦下的；首轮真实执行的大部分失败来自前置没有真正成立。
- **修正方向**：L3 的“测得对吗”应拆成三件：预期对契约（评审 + 契约引用可追溯）、场景已激活（每个场景必须有激活证据，前置未成立记 FAIL/conditional_not_triggered 而不是 WARN 或 skip）、判据对样本（现有的判据自证）。“判据能红”是必要条件，不是充分条件。

## 二、偏乐观的论断

### 4. 只有一个测试层级：把“公开面观察不到”当成“可以合法跳过”

- **论断**：SIT 只经公开面观察；观察不到的归 NOT_OBSERVED(protocol_unobservable)，合法 skip。
- **问题**：观察边界不等于验收边界。公开面看不到的内部机制（状态迁移的边界条件、并发与时序、迟到事实）在下一层（组件级，针对真实产品类）是可以验证的；直接 skip 等于放弃这部分验收。
- **修正方向**：方法论需要“分层验收”：每个场景标明由哪一层承接；只有所有层都观察不到才允许 protocol_unobservable。测试层级的判断交给测试方，不能用“开发仓有单测”抵扣。
- **2026-11-17 更正（上一条修正方向本身有误，v4.0 已按它改，v4.1 撤回）**：
  - **错在机制**：“转下一验收层（组件级）”让测试自造内部事实（直接调用内部类、注入内部状态），验的是实现而不是特性；特性档没有规定的内部机制，测试也无从判定对错。“所有层都观察不到才合法不判定”则把特性缺可观测性当成了测试可以接受的边界。
  - **修正后的论断**：验收只做 SIT。观察不到时按对外契约 → 进程日志 → 持久化数据（Redis/DB）逐级取证；三面都观察不到不是判定态，而是特性缺陷：提“特性不可观测”issue，报告记覆盖缺口，MUST 阻塞放行。NOT_OBSERVED 只保留 `trace_missing`（原则上可观察、本次没采到）；`protocol_unobservable` 撤销；合法不判定只剩 EXCLUDED、UNSUPPORTED。
  - **D1 页面**：v4.1（脚本 `insight/insight-deck-D1章节稿-v1.1.js`）只改第 6 页 L3 行、第 8 页 Fixture 列说明（去掉“验收层前缀”）、第 19 页六态与 reason_code，备注写明撤回理由。

### 5. 线性流程“契约 → 设计 → testplan → 并行实施”：假设前期就能写定激活条件

- **论断**：testplan 作者在实施前定稿场景、stub 规格和执行策略，四方据此并行推进。
- **问题**：场景能否被激活、需要什么样的替身，很多只有对真实被测物运行才会暴露（配置细节、产品默认策略、重试节奏与窗口参数的冲突、错误必须符合真实提供方格式才会被分类）。纯线性流程没有从执行回流到 testplan/fixture 规格的通道，“一个 stub 够用”这类前期判断会系统性偏乐观。
- **修正方向**：在流程中加“首次真实执行 → 回写 testplan 与 fixture 规格”的回流环，并把“激活条件已在真实被测物上验证”作为 testplan 定稿的条件之一。

### 6. 跨特性“跑而不写” + ID 级依赖 + 影响分析：前提在现实中多数不成立

- **论断**：依赖的既有能力交给相关 FEAT testplan 验证；依赖细到 ID 级，CI 据此做影响分析与自动重跑。
- **问题**：这要求上游 testplan 存在、规范、可执行，且恰好覆盖本特性消费的那部分行为。现实中这些前提大多不满足；方法论没有给出前提不满足时的退路，结果是“委托出去的部分没人测”。即便上游存在，它也不会构造本特性制造出的状态（这一点原文已列为例外，但没有推广）。
- **修正方向**：“跑而不写”改为有条件：上游 testplan 存在且覆盖被消费行为时才委托，否则本特性自己写；ID 级依赖与影响分析标为远期目标，以“上游规范化”为前提。

## 三、不完整的论断

### 7. L4 版本锚只认版本号

- **论断**：子特性加 since_version / last_modified，跨版本做分歧登记。
- **问题**：同一个版本号可以对应内容不同的制品（已发布制品与源码构建不一致），版本号和 `>=` 区间都标识不了“到底测了什么”。L4 关注的是规范版本间的判定分歧，没有覆盖“被测物身份”。
- **修正方向**：L4 增加被测物身份记录：发布基线、构建来源、制品校验和分别登记；结论只对登记的被测物成立。

## 四、经实践检验成立的论断（保留）

- 稳定 ID、删除不复用：实践中避免了编号混乱；但“删除”必须可机读，否则残留引用查不出来——这是对原规则的补强，不是推翻。
- 六态 + reason_code：区分“没测”与“测了失败”在实践中有用；需按上面第 1、3 条收紧 UNSUPPORTED 与 conditional_not_triggered 的定义。NOT_OBSERVED 只保留 `trace_missing`（见第 4 条 2026-11-17 更正）。
- 分歧必须登记、正式化后再对齐：本轮唯一一次契约与实现分歧就是按这个纪律收敛的，论断成立。
- 测试由测试组开发、验收测试不进开发仓：成立。
