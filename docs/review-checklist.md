# 评审 Checklist：Testplan / PR / Issue

面向测试组的质量自查与互查清单。覆盖三个环节：写测试设计（testplan）→ 提交变更（PR/MR）→ 报告缺陷（issue）。

**怎么用**

- 条目分两级：`[M]` 为准入门槛，任一不满足即打回；`[S]` 为质量项，不满足需在评审中说明理由。
- 作者提交前自查一遍，评审人按同一份清单过。评审意见尽量引用条目编号（如 "T-M4 不满足"），减少来回解释。
- **编号只增不改。** 新增条目一律追加新号（含 `T-M1a` 这类插入号），已有编号不复用、不重排，保证历史评审意见里的引用长期有效。分级调整会在原编号处留指引。
- 第 1 章 [M] 条目较多，建议**两遍过**：第一遍只过 1.1（事实来源一致性），引用站不住的话后面几节没有意义；第一遍通过再过其余。
- 清单是下限不是上限。它拦掉的是反复出现的问题，不替代对方案本身的判断。

**三者共同的一条原则**：降低接收方的认知成本，并把自己的判断暴露成**可被反驳**的形式。写得让别人无从质疑，和写得让别人无从下手，是两回事。

---

## 1. Testplan 质量

测试设计的核心判据是**可追溯性**——好的 testplan 是从契约与特性文档推导出来的，不是从"我能想到什么"堆出来的。

> **本章的两类失效模式。** 早期版本只防住了第一类：作者**漏了**什么（该覆盖的没覆盖、该写清的没写清）。实际评审中更高频、也更隐蔽的是第二类：作者**写错了**什么——引用做了、矩阵做了、覆盖台账也做了，但引的是旧版本、断言和引文相反、文档内部三处互斥。1.1、1.3、1.4 三节专治第二类。各条的实证来源见 `docs/review-checklist-gap-analysis.md`。

### 1.1 事实来源与引用一致性 [M]

**引用了 ≠ 引对了。** 这一族防的是最隐蔽的失效：文档规规矩矩引了特性档和低层设计，然后写了和引文相反的断言——它能顺利通过"有没有引用"式的自查。

| 编号 | 条目 | 说明 |
|---|---|---|
| T-M1 | 事实来源显式引用 | 所测特性能对应到特性档（FEAT-NNN）与低层设计文档的具体章节，在文档内显式引用。禁止凭被测实现反推需求。 |
| T-M1a | 所引文档为现行版本 | 引用前核对来源文档的 frontmatter（`status` / `updated`）。若基于历史版本裁剪范围，必须写明所依据的版本与日期，并说明与现行版之间的差异**是否影响范围结论**。拿冻结版当依据把大片契约划出范围，是范围失效的典型路径。 |
| T-M1b | 断言不得与所引文档冲突 | 期望值与来源文档的规定不一致时，**先走裁定，不得直接写成期望绿灯**。发现实现与文档不符，正确动作是提冲突单，而不是把实现现状固化成契约。 |
| T-M1c | 引用精确且等级保真 | 引用要落到章节号；MUST / SHOULD / MAY 等级不得漂移；不得把低层设计的条款记在特性档头上（反之亦然），也不得把某文档的默认值安到另一份文档名下。 |
| T-M1d | 具体值可逐字定位 | 断言里出现的错误码、字段名、阈值、状态枚举，**每一个**都要能在来源文档里逐字找到。 |

> **T-M4 是必要不充分的。** 一个错误码即使写到了字段与取值、枚举用了全称，完全满足"可判定"，仍可能在来源文档全文无出处。**可判定**和**有出处**是两件事：T-M4 管前者，T-M1d 管后者，必须同时过。

### 1.2 覆盖与场景设计 [M]

| 编号 | 条目 | 说明 |
|---|---|---|
| T-M2 | 场景矩阵有稳定 ID | 每条场景有不随代码演进而失效的编号。矩阵 ID 不绑定测试类名/目录（代码会改名，设计不该跟着改）。 |
| T-M3 | 双向覆盖台账 | 既能从用例查到它验的是哪条契约，也能从每条契约查到被谁覆盖；**不覆盖的必须显式列出并写明原因**（原因的硬要求见 T-M17）。覆盖率数字的价值不在数字，在于剩下的部分是被点名的而不是被遗漏的。**回测中产出最高的一条。** |
| T-M4 | 期望值可判定 | 写到字段与取值，枚举用全称。"返回正常""符合预期""流程走通"一律不算期望值。须与 T-M1d 同时满足。 |
| T-M5 | 分层完整 | 正例、异常、边界、时序/并发、**权限与状态机非法迁移**五类都有交代；确实不适用的写明原因。缺口在实践中几乎总是集中在后两类。 |
| T-M21 | 可观察性判据有出处 | 凡是断言"客户端应看到 X"，都要能说明 X 是对外 wire 契约，而不是内部诊断标识或适配层私有 SPI。断言写在内部语言上的用例，即使挂了也不构成缺陷——这是质量下限。*（原 T-S4，2026-09-02 由 [S] 提为 [M]）* |

### 1.3 文档内部一致性 [M]

同一份文档自己跟自己打架，评审者无法判断哪个说法作数。

| 编号 | 条目 | 说明 |
|---|---|---|
| T-M9 | 场景 ID 唯一 | T-M2 只要求 ID 稳定，不保证唯一。同一编号被两个场景占用，执行集里会并列出现两条同 ID 用例。 |
| T-M10 | 计数与清单闭合 | 文中声明的条数须等于矩阵实际行数；P0 / Full / Smoke 各执行集里的每个 ID 都要在矩阵中存在，反之矩阵中每条都要在某个执行集里有归属。 |
| T-M11 | 同一不变式全篇同一口径 | 同一个断言在不同用例里不得给出互斥写法（一处断言成立、一处明写不再断言、一处断言不成立）。 |
| T-M12 | 单行内自洽 | 同一场景行的前置条件、步骤、期望结果、Fixture 不得互相矛盾（例如前置写"当前未实现"而 Fixture 列写已落地；前置要求真实外部凭据而全篇声明用 mock）。 |

### 1.4 边界自洽 [M]

| 编号 | 条目 | 说明 |
|---|---|---|
| T-M13 | 不违反自己声明的观察边界 | 文档声明了黑盒边界（"不读 SUT 内部状态、日志或存储"），矩阵里就不能出现读内部状态或私有日志前缀的断言。要么改断言，要么改边界声明，不能两存。 |
| T-M14 | 测试层次归属清晰 | 单元测试、集成测试、验收场景分表或分章，不混排进 SIT 场景矩阵。混排会让"验收通过"的口径失真——单测全绿替代不了验收结论。 |
| T-M15 | 断言在声明拓扑下可验证 | 期望结果里的每个观察点，在拓扑章给出的部署形态中必须存在观察面。拓扑是单服务，就不能断言"被调方运行时里的占额"。 |

### 1.5 治理与越权 [M]

testplan 是**记录契约的**，不是**制定契约的**。这一族是 P-M7「别队资产不单方面改」的精神在测试设计侧的延伸。

| 编号 | 条目 | 说明 |
|---|---|---|
| T-M16 | 不替代上游变更流程 | testplan 不得注销、反转或新增特性档 / 低层设计的契约条款，也不得在测试计划里记载生产侧的新出参或新接口。发现契约需要改，动作是**提变更单并在文中引用变更单编号**。无论结论对错，绕过流程本身就是错的。 |
| T-M17 | 不覆盖项须指名承接方 | T-M3 要求写明原因，但原因可以是空话。两条硬要求：**(a)** 排除理由须经技术可行性检验——"需故障注入""结构性无法覆盖"这类说法要逐条验证是否真的做不到；**(b)** 承接方须**指名到模块 + 用例**，只写"由上游承接"等于覆盖黑洞。 |

### 1.6 可复现锚点 [M]

| 编号 | 条目 | 说明 |
|---|---|---|
| T-M6 | 可独立执行 | SUT 版本与启动参数、依赖桩、数据前置、清理动作齐备，他人照做能得到同样结论。文中给出的分组名、套件名、执行命令必须真实存在且跑得出所声明的集合。 |
| T-M18 | 事实来源须为组织仓 + 不可变锚点 | SUT、example、脚本的引用必须指向**组织仓路径 + commit 或 tag**。指向个人 fork 且无锚点的，对方一改历史整篇即不可复现。 |
| T-M19 | 被测物版本可校验 | 二进制与源码的对应关系要有运行时可断言的指纹。沿用旧版本坐标、需先本地构建才能拾取新产物的，一旦漏做就会跑着旧产物**全绿**——这是最危险的假绿路径。 |
| T-M20 | 资源不硬编码独占 | 端口、缓存 key 前缀、临时目录须可配置或动态分配，并写明清理动作。全固定端口在并发流水线上必撞。独立前缀 + 用后清理是该条的正面写法。 |

### 1.7 文档形态与纪律 [M]

| 编号 | 条目 | 说明 |
|---|---|---|
| T-M7 | 保持为纯设计文档 | 真机记录、缺陷对时、验证结论不进 testplan，统一进用例细档的进展章节。设计与进展混写会让文档很快失去权威性。 |
| T-M8 | 存疑项显式化 | 判不了、测不了、待澄清的条目单列。显式承认盲区，比硬凑覆盖率诚实，也更有用。 |

### 1.8 质量项 [S]

| 编号 | 条目 | 说明 |
|---|---|---|
| T-S1 | 标注诊断价值 | 每条场景写清"这条挂了说明什么"。挂了不知道意味着什么的用例，回归时会被直接跳过。 |
| T-S2 | 跑序无关 | 用例可单独执行，不依赖前序用例留下的状态。 |
| T-S3 | 优先级分级 | 标出准入必跑集与全量集。**P0 集合内的用例必须当前可跑且应当全绿**——P0 里躺着未落地的用例，这个门禁就是摆设。 |
| T-S5 | 看守用例显式标注 | red-first（缺陷看守）用例注明预期为 FAIL 及关联 issue，避免被后人当成坏用例删掉。 |
| T-S6 | 变更记录 | 附录记录设计级变更（基线差异、契约调整），便于回溯当初为什么这么设计。 |
| T-S7 | 目录规范符合 | frontmatter 字段按其语义填写（例如"部署单元"字段不要填成代码仓名）；章节结构符合所在目录 README 的规定，缺章须显式写豁免说明。 |
| T-S8 | INCONCLUSIVE 与 FAIL 分层 | 依赖外部条件（下游未被调用、日志不存在、外部模型或依赖服务不可用）时判 INCONCLUSIVE 而非 FAIL，并写明判定条件。这条决定了红灯是"发现缺陷"还是"环境没到位"。 |

> T-S4 已于 2026-09-02 提为 [M]，见 T-M21。原编号保留在此说明中，避免旧评审意见里的引用失效。

### 1.9 反向判据（出现即需警惕）

- **一轮跑完全绿。** 最常见的原因不是实现完美，而是期望值照着实现写的。
- **文档规规矩矩引了特性档，但断言和引文相反。** 比"没引用"隐蔽得多，因为它能通过"有没有引用"式的自查。
- **把"当前实现就是这样"写成期望值。** 上一条的孪生形态——不是照着实现改期望，而是发现实现与文档冲突后，选择站实现那边并保持沉默。
- **附录里出现"某条 MUST 在当前实现已不存在，故不再单列场景"。** 这是 testplan 在替上游做裁定，无论结论对错，流程都错了。
- **范围章的排除理由是"结构性无法覆盖"，却没指名谁来覆盖。** "结构性"三个字承担了太多，需要逐条检验。
- 期望值或用例名里出现只有读过实现才知道的内部标识。
- 出现"验证功能正常""确认无异常"这类不可判定的描述。
- 矩阵 ID 与测试类名一一耦合，改个类名就要改设计文档。
- 报得出覆盖率百分比，但答不出没覆盖的具体是哪几条契约。

### 1.10 样本对照

- **正面**：对不确定的通道，先写一个全字段递归扫描的 helper 摸清实际结构，再据此写硬断言。先观察后断言，能避免大量基于假设的错判。
- **正面**：需要独占资源时用独立前缀 + 用后清理，而不是硬编码固定端口与固定 key。
- **反面**：把内部诊断用的标识当作客户端可见契约来断言。特性档里写明是内部字段，用例却要求它对外可见——这类用例即使挂了也不构成缺陷。
- **反面**：以某份冻结版特性档为依据，把一整族 MUST 划出测试范围，而现行版该族仍然有效且条数可观。

## 2. PR / MR 质量

变更提交的核心判据是**可审查性**。评审者的注意力是稀缺资源，PR 的写法决定了这份注意力花在哪。

### 2.1 准入项 [M]

| 编号 | 条目 | 说明 |
|---|---|---|
| P-M1 | 单一意图 | 一个 PR 解决一件事。顺手做的重构、格式化、改名单独提。这是最高频的减分项：它把评审注意力耗在噪声上。**文档类 PR 同样适用**——一次提多篇互不相干的文档，只要其中一篇需返工，可合的那几篇也会被整体卡住。 |
| P-M2 | 描述可脱离 diff 读懂 | 背景与动机（为什么改）、方案与取舍（改了什么、为什么不用别的做法）、验证方式、影响面。四段缺一不可。 |
| P-M3 | 验证有证据 | 代码类 PR：给出实际执行的命令、结果、环境。文档类 PR：给出**引用核对记录**（见 2.4）。"本地测过没问题""应该没影响"不算验证。 |
| P-M4 | 行为变更有用例对应 | 代码类 PR：修了缺陷就要有一条**在改动前会失败**的用例。文档类 PR：契约类变更须说明**哪些既有用例的断言会随之改变**（见 2.4）。 |
| P-M5 | 无敏感信息与无关夹带 | 内网 IP、主机名、token、个人路径不得入库；不夹带与本次意图无关的改动。 |
| P-M6 | 共享仓归属清晰 | 仓库是全组共用的。提交内容要么通用、要么命名带辨识度标明专属归属；不得让专属内容看起来像通用资产。 |
| P-M7 | 别队资产不单方面改 | 涉及他人模块或团队级配置的改动，先提议再动，不在自己的 PR 里顺手改掉。 |
| P-M8 | 推送前确认 | 未经明确批准不推分支、不建 MR，成果先给相关方过目。 |

### 2.2 质量项 [S]

| 编号 | 条目 | 说明 |
|---|---|---|
| P-S1 | 规模可控 | 单个 PR 的有效 diff 控制在数百行量级，超出考虑拆分。评审有效性随规模断崖下降。 |
| P-S2 | 作者自审留言 | 在 diff 上主动标注非显然的选择，替评审者省掉一轮提问。 |
| P-S3 | commit 粒度可回滚 | 每个 commit 自洽，message 说清 why 而不只是 what。 |
| P-S4 | 关联可追溯 | 关联到 issue 编号或设计矩阵 ID。 |
| P-S5 | 文档同步 | 改了设计就同步台账，改了用例就同步进展记录，不留下文档与代码互相矛盾的状态。 |

### 2.3 反向判据

- 评审意见大量集中在"这里能不能顺便……"——说明 PR 边界从一开始就没划清。
- 描述里只有 what 没有 why，评审者被迫从 diff 反推意图。
- 验证段出现"理论上""应该"。
- 一个 PR 同时动设计文档、用例、脚本、配置，且彼此无关。
- 评审者提的第一个问题是"这个改动是为了解决什么问题"。
- 一个文档 PR 里几篇文档的评审结论不一致（有的可合、有的需返工），导致只能整体挂起——说明 P-M1 在提交时就没执行。

### 2.4 文档类 PR 的适配口径

第 2 章的默认假设是代码 PR。提交 testplan、设计文档、规范这类**没有可执行产物**的 PR 时，P-M3 与 P-M4 按下面这样落地：

- **P-M3 的"验证" = 引用核对记录。** 逐条列出：引了哪份文档的哪个章节号、该文档的版本与日期（`status` / `updated`）、断言里的具体取值在来源文档中的出处。这份记录就是文档 PR 的测试报告，评审者据此抽查，而不是重新通读一遍来源文档。等价于对第 1 章 T-M1a~T-M1d 的自查留痕。
- **P-M4 的"用例对应" = 断言影响清单。** 若改动涉及契约理解（新增/修订/推翻某条条款的解读），须列出哪些既有用例的断言会随之改变、是否需要同步改代码、以及在同步完成前该用例的判定口径（参考 T-S8 的 INCONCLUSIVE 分层）。纯排版、错别字类改动写"无契约影响"即可。
- **拆分粒度。** 一篇文档一个 PR 是默认值。确需合并提交的，必须是同一特性、同一结论走向的文档。

## 3. Issue / 缺陷质量

缺陷报告的核心判据是**接收方零成本复现 + 结论有据**。缺陷被打回的两大原因永远是不可复现和判据不足。

### 3.1 提交前 pre-flight 三问 [M]

任一未做，一律不许提。这三问是从实际教训里固化下来的：

1. **全字段扫过没？** 对目标通道至少跑一次递归全字段遍历。字段级观察（某个字段为空）**不可**直接放大为通道级结论（整条通道没有该信息）——除非全字段扫描确实全空。
2. **交叉通道验过没？** 同一份底层信息通常有多条对外通道。任何"客户端观察不到 X"的结论，必须至少在两条通道上验证过，任一通道命中即证伪。
3. **特性档核对过没？** 判据里出现的每个字段名都要能在特性档里定位到"是不是客户端可见 wire"。自造名词和内部标识是这一步最容易翻车的地方。

### 3.2 准入项 [M]

| 编号 | 条目 | 说明 |
|---|---|---|
| I-M1 | 三问已过 | 见 3.1。 |
| I-M2 | 现象与推断分离 | "我观察到什么"与"我认为原因是什么"分开写，后者明确标注为推测。 |
| I-M3 | 复现最小且确定 | 完整请求与响应、被测版本/commit、环境、时间点。步骤能被别人原样重放。 |
| I-M4 | 判据有出处 | 引特性档或契约的具体条款，说明为什么这是缺陷而不是预期行为。 |
| I-M5 | 影响面与优先级有论证 | 说清影响哪些场景、什么条件下触发、为什么是这个优先级，不拍脑袋定级。 |
| I-M6 | 与历史 issue 的关系说清 | 是否同族、此前的修复为何没触达。**用叙述讲清楚，不要堆多 issue 交叉关系表**——绕的表述会让人看不出真实结论。 |
| I-M7 | 草稿先过目 | 缺陷先写成草稿（`docs/issues/draft-<slug>.md`）给相关方预沟通，认可后再正式提交。 |

### 3.3 质量项 [S]

| 编号 | 条目 | 说明 |
|---|---|---|
| I-S1 | **定位到代码层** | 不止于"哪一层出问题"，要给到文件、类、方法，指出具体是哪一行做了吞掉/改写/短路。详见 3.3.1。这是最能拉开质量差距的一项。 |
| I-S2 | 预答开发反问 | 把"是不是你环境问题""是不是配置没开"这类问题提前答掉。 |
| I-S3 | 修复建议与验收方式 | 建议改动方向，并写明修复后哪条用例应当转绿。 |
| I-S4 | **场景一步步说清，并交代影响面** | 正文主体是可顺读的场景叙述，不是结论堆叠；叙述末尾把"这会导致谁、在什么情况下、受到什么影响"讲具体。详见 3.3.2。 |
| I-S5 | 附看守用例 | 提交一条 red-first 用例守住该缺陷，防止回归。 |

#### 3.3.1 什么叫"定位到代码层"

"某一层没上报"是现象的换一种说法，不是定位。合格的代码层定位包含：

- **精确坐标**：文件路径 + 类名 + 方法名，能给行号最好，但必须注明**基于哪个 commit / 哪个版本的源码**——行号会漂，脱离版本的行号是误导。
- **被测物与源码的对应关系**：说明手上跑的二进制（jar/镜像）对应哪个 commit 或构建号。对不上的话，整个定位可能指向了另一份代码。
- **关键代码做了什么**：具体是哪一行捕获了异常、做了类型转换、走进了哪个分支、提前 return 了。把那几行贴出来。
- **调用链**：从对外入口到出问题的方法的路径。开发关心的是"请求进来之后在哪一步拐弯的"。
- **为什么别处的既有修复没生效**（若相关）：例如修复做在更上层，而异常在更下层就已经被转换成正常结果，上层根本收不到。这类说明能直接省掉开发一轮排查。
- **推断与实证分开标注**：纯读代码得出的结论标注为静态分析；有日志、断点、调试输出支撑的标注为运行时实证。两者混写会让开发无法判断可信度。

> 反面：只说"远程调用失败没有上报"。
> 正面：指出请求经由哪个入口进入、在哪个映射类的哪个方法里捕获了连接异常并转换成了正常的工具结果、因此更上层执行器里已有的那处修复根本触达不到——开发拿到就知道改哪儿。

#### 3.3.2 影响面要交代到什么程度

I-M5 要求的是**定级有论证**（对外的优先级结论）；这一条要求的是**在场景叙述里把后果讲具体**，让开发不必自己推演。至少覆盖：

- **受影响的对象**：哪类调用方、哪些业务场景、哪些已通过的用例可能被波及（回归面）。
- **触发条件的普遍性**：必现，还是只在特定配置、特定时序、特定拓扑下出现。偶现的要给出观察到的频次。
- **后果的性质**：是结果错误、状态错误，还是仅可观测性缺失。**特别标注"静默失败"类**——错误被吞成正常结果、任务实际失败却报成功，这类危害显著高于显式报错，因为调用方没有任何机会做补偿。
- **是否有绕过或缓解手段**：有没有配置开关、重试、旁路通道能规避。有缓解手段会直接影响修复紧急度。
- **是否阻塞验收**：说明这条缺陷是否卡住某个特性的准入结论。


### 3.4 反向判据

- 开发的第一句回复是"能给下复现步骤吗"或"这是预期行为"。
- 证据是字段级的，结论却是通道级的。
- 只在单一通道上观察就下"客户端不可见"的结论。
- issue 提出后靠追加评论反复修正结论——追多了开发看不出最终结论是什么。发现漏做，优先删评论、改正文，而不是继续追评论。
- 判据依赖的字段其实是内部诊断标识。

### 3.5 样本对照

- **定位质量的正反例**见 3.3.1 末尾的对照。
- **推断过度的反面**：以某通道的一个字段为空，推出"整条通道没有子任务信息"，未做全字段递归扫描也未交叉验证，最终撤回。字段级证据支撑不起通道级结论。
- **影响面缺失的反面**：只写"该接口返回错误"，没说明是所有调用方必现还是特定配置下偶现、有没有绕过手段。开发无法判断该排在什么优先级，issue 就会一直躺着。

## 4. 模板片段

### 4.1 PR / MR 描述

```markdown
## 背景
<为什么要做这个改动。现象、触发场景，或关联的 issue / 矩阵 ID>

## 改动内容
<改了什么。多个文件时按意图分组，不逐文件流水账>

## 方案取舍
<为什么这么做；考虑过但没采用的做法及原因。无非显然选择可写「无」>

## 验证
<实际执行的命令 + 结果 + 环境>
<行为变更类改动：说明哪条用例在改动前会失败、改动后转绿>

## 影响面
<影响哪些模块/场景；是否涉及团队级或别队资产；是否需要他人同步改动>
```

### 4.2 Issue 草稿（`docs/issues/draft-<slug>.md`）

```markdown
# <一句话结论：什么条件下、什么行为、与什么预期不符>

## 结论摘要
<3~5 行说清缺陷是什么、影响什么、优先级建议及理由>

## 场景说明
<一步步顺读的场景叙述：怎么触发、期间发生了什么、在哪一步偏离预期>

## 影响面
<受影响的调用方 / 业务场景 / 可能被波及的已通过用例>
<触发条件：必现还是特定配置、时序、拓扑下出现；偶现的给出频次>
<后果性质：结果错误 / 状态错误 / 仅可观测性缺失；是否属「静默失败」（失败被报成成功）>
<是否有绕过或缓解手段；是否阻塞某特性的验收结论>

## 实测证据
<完整请求 / 响应、日志片段、观察到的字段与取值>

## 代码层定位
<被测二进制对应的 commit / 构建号>
<文件路径 + 类名 + 方法名（给行号须注明基于哪个 commit）>
<关键代码片段：哪一行捕获 / 转换 / 短路了>
<调用链：从对外入口到出问题方法的路径>
<若相关：为什么别处的既有修复触达不到这里>
<标注哪些是静态分析推断、哪些有运行时实证支撑>

## 判据
<引特性档 / 契约的具体条款，说明为何属缺陷而非预期行为>

## Pre-flight 自查
- 全字段扫描：<做了什么扫描，结果>
- 交叉通道验证：<在哪些通道上验过，结果>
- 特性档核对：<涉及字段是否为对外 wire，出处>

## 与历史 issue 的关系
<是否同族；此前修复为何未触达。用叙述，不堆关系表>

## 复现条件
<版本 / commit、环境、启动参数、依赖桩、数据前置、时间点>

## 预答可能的反问
<提前答掉环境、配置、版本类质疑>

## 修复建议与验收
<建议方向 + 修复后哪条用例应转绿>
```

## 附：一页速查

如果只记三条：

- **Testplan**——引用要引对、引现行版本，断言不许和引文相反；期望值既要**可判定**又要**有出处**；没覆盖的要点名承接方，不要沉默。
- **PR**——一个 PR 一件事（文档 PR 同样适用）；验证段给证据不给保证，文档类 PR 的证据是引用核对记录。
- **Issue**——三问过完再提；定位到代码层（文件/类/方法/哪一行），并把影响面讲具体，而不是只报现象。
