# 协作与扩展体系

本页回答两个问题：**能力从哪些点接进来**（扩展点矩阵），以及**一次请求的数据与事件怎么流**（端到端链路）。


## 一、扩展点矩阵

| 扩展 | 位置 | 接入方式 |
|---|---|---|
| Agent Handler | `ports/handler.py` | 显式注入或 discovery / registry 装配 |
| 本地框架 | `adapters/outbound/framework/`、`agentcore/` | adapter 内部翻译原生输入 / 输出 |
| 远端 Agent | `adapters/outbound/remote/`、`versatile/` | Card / client / stream adapter / failure rules |
| SkillHub | `adapters/outbound/skillhub/` | 配置与工厂生成中间件代理 |
| 状态后端 | `ports/cache.py`、`state_store.py` | Redis / DB / fallback 实现 |
| 入站通道 | `ports/contract.py`、`adapters/inbound/rest/channel.py` | `RestChannel` 解析与投影 |

### 参考宿主

`deploy/host_app.py` 展示两档后端：默认 fixture 用于确定性契约验证，`RUNTIME_BACKEND=agentcore` 用于真实 workflow 贯通。这里的 `RUNTIME_BACKEND` 是参考宿主自己的旋钮，不是 runtime 配置项。两者共用同一组合根和路由，差别只在 Handler 注入。

### 宿主义务

宿主必须提供可达的公开 URL、必要的 Redis / secret、进程生命周期、鉴权与观测；runtime 提供 Handler / Task / stream 语义和 readiness 视图，但不替宿主定义业务健康检查端点。宿主对导出的 `app.state.readiness` 负责接入自己的探针。

### 容器验证

`deploy-e2e/` 是交付级验证装置，不是生产部署模板。`Makefile` 的 `e2e` 聚合真实脚本，覆盖 agent-core、A2A、远端、客户端工具、总线、回调、断连、端点盘点、生命周期配置、对等比对和等待窗口。

## 三、完整调用链（端到端）

### 入站到执行

```text
HTTP body
  → channel / protocol adapter
  → ServeRequest + CallContext
  → ServeOrchestrator
  → AgentHandler.stream_query
  → QueryChunk
  → projection / A2A event queue / SSE
```

每一跳只负责自己的边界转换。`domain/aggregate.py` 只聚合领域结果；它不解析 FastAPI 请求，也不理解 A2A protobuf。

### 事件观察与总线

标准 Task 状态和业务事件可经观察者进入 `application/bus_consume.py`、`adapters/outbound/bus/` 的投影与发布链路。消费流程区分 admission、处理、发布、ack / reject 和重试；重复消息通过 event ID / projection store 控制。

### 远端批次

`application/remote_batch.py` 负责深度、预算、成员屏障和回填分类；`adapters/outbound/remote/` 负责 HTTP / SSE / callback 细节。成员输出回到统一 `QueryChunk` 后再由上层投影，避免远端协议污染入口。

## 四、协作边界总结

agent-core 负责 Agent 语义与会话内执行，runtime 负责托管、协议、状态与生命周期。两者的接触面只有三处：运行资源登记（Runner）、执行入口（`run_agent_streaming` / `run_workflow_streaming`）、原生输出帧到 `QueryChunk` 的转换。除此之外，runtime 不理解 agent-core 的内部对象，agent-core 也不知道 A2A 与 REST 的存在。
