## 发现

### 发现 1（锚点缺口，建议合入前处理）：探针处置宽于 L1，L1 未配套修订

规格 §6 探针处置表把「正向因果闭合的 `GUARDRAIL_DENIED`」列为健康关门证据、把 `INPUT_REJECTED`
定为「计分母但只释放名额保持 `HALF_OPEN`」，依据均写「2026-11-20 裁定」。但 docs main 的特性档
§5.1.6 至今仍是「健康结果包括正常完成、无系统异常的预期业务失败和 awaiting_answer」三类，两处新语义
都不在 L1 文本里。规格自己声明「需求真源是 FEAT-112 L1 特性档」，生效状态段也只提了「DA L2 旧表述由
配套 PR 同步刷新」，没有提 L1。

这正是原差异三的裁决结果，裁决本身没有问题；问题是裁决的 L1 载体缺失。建议二选一：
① 需求侧出 L1 §5.1.6 配套修订（把健康结果清单与 `INPUT_REJECTED` 处置写进 L1），与 !581 同批合入；
② 规格探针表两行标注「待 L1 配套修订生效」。否则「规格宽于需求真源」与无损性承诺自相矛盾，
测试侧也无法以 L1 为准裁掉这两行的验收依据。

### 发现 2（文内不同步）：core error 通道范围表漏标 #862 例外

§5 判定序第 9 步已写明例外（完整闭合的「拒绝耗尽型 `MAX_ITERATIONS`」落第 11 步），§7 差距 5 也有同样
的判定序限定；但 §5「core 结果轮 error 通道范围」表第三行「达到最大迭代次数 → `MODEL_SERVICE_FAILURE`」
没有标注该例外。同一语义文内三处、一处缺口，照抄该表的实现或测试会漏掉例外。建议该行补注
「拒绝耗尽型除外，见第 9/11 步与 §7 行 5」。

### 发现 3（覆盖性表述）：L1 第二行的对应有未言明的识别前提

§3 覆盖性自检称七行与七个枚举值「一一对应」。但 §2 规定 `BUSINESS_FAILURE` 只认显式结构化
`result_type=business_failure`；L1 第二行里的「正常工具业务错误」若未产生该结构化事实，实际会沿判定序
落到第 12 步计入分子。这个保守缺省本身符合 L1 §5.1.3 第三段原则，不是语义错误，但「一一对应」读起来
像无条件成立。建议在 §3 补一句：该行的对应以显式结构化事实为前提，无事实时按保守缺省归系统异常。

### 发现 4（措辞，低优先级）：「denied 事实」一词易与 occurrence 字段混淆

§4 规定 `guardrailDeniedEvidence` 仅为 occurrence 观测、「不进入分类判定」；判定序第 11 步写
「有 denied 事实且最终失败因果正向闭合」。两处的「denied 事实」不是同一个东西（后者指护栏结构化因果
事实）。建议第 11 步改写为「有护栏结构化因果事实且正向闭合」，避免被读成消费 occurrence 布尔。
