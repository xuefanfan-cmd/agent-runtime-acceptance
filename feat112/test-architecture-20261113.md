## 一、架构概览

| 层 | 组成 | 职责 |
|---|---|---|
| ① 契约与基线 | 特性档快照 `05af9cc3`、testplan、cases、L2（只作参考） | 预期只取自特性档 |
| ② 治理层 | `Feat112Contract`、`Feat112Coverage`、`Feat112ArchitectureTest` | 条款出处钉版本；ID 对账；6 条结构规则 |
| ③ 用例层 | `integration/`（13 类，公开面）、`component/`（1 类，真实产品类） | 按验收层分目录，`@Covers` 声明场景与层 |
| ④ 通用结果层 | `Scenario`、`AcceptanceExtension`、`EvidenceChecks`、`ScenarioVerdict`、`ArtifactIdentity`、`AcceptanceReport` | 前置 / 激活 / 验收三段记录，结论由固定顺序推导，JUnit 状态只是投影 |

| ⑨ 被测物 | 载体 jar、故障注入 stub、产品类 | — |
| ⑩ 产物 | 证据 JSON、结果 JSON、`summary.md` | 每条结果带发现、期望、实际、证据引用、被测物身份 |

依赖方向（由结构规则强制）：用例 → 夹具（判据 / 驱动 / 部署）→ 通用结果层；判据不依赖驱动和部署；用例只能经记录的 Finding 下结论，不能直接断言。

## 二、是否合理

**合理的部分：**
1. **判定与执行分离落到了结构上。** 驱动只产出观察，判据是纯函数，结论由结果层统一推导；结构规则禁止用例绕开 Finding 直接断言。
2. **前置、激活、验收三段分开记账。** “没走到”记 conditional_not_triggered，不会被当成产品缺陷，也不会被当成通过（E3、G8 就是实例）。
3. **验收层按可观测边界划分，而不是按部署方式。** 公开面看不到的机制（B7、E9、E11）由组件级针对真实产品类验收，不在 HTTP 上编造字段。
4. **预期来源被代码约束。** 规则出处只能经 `Feat112Contract` 引用特性档 `05af9cc3`，结构规则会拦截引用 L2 或实现的写法。

**不合理或欠缺的部分（按影响排序）：**

| # | 问题 | 本轮复核中的实际后果 | 建议 |
|---|---|---|---|
| 1 | **只绑定了 ID，没绑定语义。** 结构规则保证 testplan 的 ID 和 `@Covers` 一一对应，但不检查测试是否真的按 testplan 的前置和期望实现 | C7：testplan 改了前置（窗口短于静默期），测试没跟着改，出口 4 前半句一直没被严格验证；E3：testplan 写“只计分母”，测试断言样本为 0 | 给每个场景的“前置 + 期望”文本算指纹，存进代码；testplan 文本一改，结构规则就要求复核对应用例 |
| 2 | **不能离线重评。** 判据在测试运行时计算；证据虽然落盘了，但没有读取已存证据、用新版判据重算的评估器 | 这次复核要改十几条预期（E3、E4、G5、F1–F3 等），只能全量重跑，无法先在旧证据上看结论如何变化 | 增加离线评估器：按场景读取证据 JSON 和观察值，用指定版本的判据重算 |
| 3 | **结果里没有判据版本和 testplan 版本。** 结果 JSON 只记录了被测物身份，没有测试仓提交、testplan 版本 | 预期修订后重跑，结论变了，分不清是产品变了还是判据变了 | 结果和 `summary.md` 报告头写入测试仓提交、`Feat112Contract` 钉的特性档版本、testplan 提交，以及分母口径 |
| 4 | **被测物来源不完整。** `SOURCE_REVISION` 靠手工传入；core 的版本没有记录；demo 和 stub 在 solution 仓里是**未纳入版本控制的目录**，载体来源实际是“`0f5d17265` + 未跟踪文件” | 无法从结果复原被测物；也不满足你刚提的“载体用 core develop 和 solution 最新代码构建”的要求 | 由供给脚本生成构建清单（core commit、solution commit 与是否 dirty、demo/stub 所在提交、载体 sha256），写进每条结果；demo 和 stub 纳入版本控制 |
| 5 | **结构规则和覆盖对账不在 CI 里。** 测试仓整仓编译受阻，只能经 `run-feat112.sh` 旁路运行 | 规则只在有人手工跑时生效 | 拆模块或修复整仓编译后接入流水线（与此前架构评审的 G 项相同） |
| 6 | **时序和并发类场景只跑一次。** 没有复跑机制 | 此前讨论“为什么一个 bug 都没发现”时，这是原因之一 | 对 C5、C6、E1、J4 等时序敏感的场景提供复跑器，报告 pass^k |
| 7 | **组件层与载体可能不是同一次构建。** 组件层经 `feat112-product` profile 引用 M2 中的 0.1.3，载体单独构建 | 两层可能测的是不同版本的同一个门 | 同一次供给同时产出两者，并核对产品类 sha256 一致 |

## 五、超出洞察的部分（可回流洞察的候选）

1. **对照判法（O 判据族）。** 契约只说“返回既有错误”而不给具体文案时，用被测物自己在门 CLOSED 时对同一请求的响应作为基准，既不抄实现，也能判定。D1、D2 都没有这一招。可提炼为：契约引用既有行为时，以门外行为为对照基线。
2. **方法论约束本身做成可执行的结构规则。** D1 L5 讲的是 ID 双向校验；这里进一步把“只经 Finding 判定”“预期只引特性档”“判据不依赖驱动和部署”“部署形态必须声明”写成会失败的测试，并做了变异验证，证明规则能红。可提炼为：方法论约束要可执行、并且自身要能红。
3. **反向教训：ID 绑定不够。** 本轮两次语义漂移（C7、E3）都发生在 ID 完全对齐的前提下。这说明 D1 L5 的“三件绑死”只靠 ID 是不够的，还需要语义层的绑定（问题 1）。这条可以作为对 D1 L5 的修正回流。

说明：分层验收（观察不到先转下一验收层）、被测物身份、能力门只管可选能力、激活证据，这四点是本次实践先做出来、再回写进 D1 v4.0 的，所以与洞察一致，不算超出。

## 六、建议的改进顺序

1. **被测物来源**（问题 4、7）：配合“core develop + solution 最新代码”重建载体时一并做，否则下一轮结果仍无法复原。
2. **结果与报告头写入版本**（问题 3）：改动小，能立刻区分“判据变了”和“产品变了”。
3. **期望文本指纹**（问题 1）：防止本轮出现的语义漂移再次发生。——2026-11-16 已实现：`feat112/expectation-fingerprints.txt` + `Feat112ArchitectureTest#testsWereReviewedAgainstTheCurrentTestplanText`，变红已验证。
4. **离线评估器**（问题 2）：在大规模修订预期之前先有，可以把修订影响看清楚。
5. **复跑器**（问题 6）与 **CI 接入**（问题 5）：前者限时序类场景；后者取决于整仓编译能否修复。
