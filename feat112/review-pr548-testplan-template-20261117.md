## 三、测试点编号规则：确实缺失

现状：
- 模板只在“与 D1 洞察的对应”表里引用 D1 §6c 的格式 `FEAT-NNN-{domain}{seq}[-{variant}][.{point}]`，没有规定各段含义、什么时候用 `.point` 和 `-variant`、新增/拆分/撤销时怎么编号。
- FEAT-112 testplan 只有一行格式加域字母表，实际 ID 已经出现多种写法：
  - `D1a`、`G5a`–`G5c`：字母后缀，格式里没有这种写法；
  - `B1.1`–`B1.3`、`E1.1`/`E1.2`：同一场景的不同检查点；
  - `A5.1`–`A5.3`：同一期望、不同输入（阈值 0、1.5、NaN），实为变体；
  - `E5.1`–`E5.6`：拆分后前置、步骤都不同，实为独立场景；
  - `E4.1`：因为 E5 已被占用而插在 E4 后的新场景；
  - `K-rep1`、`F-reg`：没有序号，靠后缀表达类型。
- 后果：同样是 `.n`，有时是检查点、有时是变体、有时是独立场景；测试仓解析 ID 的正则不得不为 `-rep`、`F-reg` 开例外；撤销的 ID（E5、原 J09）只记在注释里，没有统一登记，可能被复用。

建议在模板中新增“ID 与测试点编号规则”一节（草案）：

1. **三级结构**
   - **场景**：§5 的一行，`FEAT-NNN-{域}{序号}`，如 `FEAT-112-C8`。
   - **测试点**：同一场景、同一前置与步骤下需要分别给出结论的检查，`{场景}.{n}`，如 `FEAT-112-B1.2`。有测试点的场景，结论取各测试点中最严重的。
   - **变体**：同一期望、不同输入或部署形态（入口、门状态、参数取值），`{场景}-{变体}`，变体名用小写短词（如 `-run`、`-stream`、`-open`、`-half`）。变体需要单独结论时，改用测试点。
2. **判断用哪一级**：前置或步骤不同 → 新场景（新序号）；前置与步骤相同、检查项不同 → 测试点；期望相同、输入不同 → 变体。
3. **域**：每个 testplan 在 §5 开头列出域字母及含义；新增域按字母顺序追加，已用的字母不改含义。
4. **序号**：从 1 开始，按新增顺序递增（不按表内位置），不重排，允许空号。插入不借用 `.n`。
5. **撤销与拆分**：撤销的 ID 永不复用，在 §5 末尾“已撤销 ID”表登记“原 ID → 原因 → 替代 ID”（如 `E5 → 拆分 → E5.1–E5.6`）。拆分后的新 ID 按第 2 条定级。
6. **类型不进 ID**：代表场景、回归冒烟等类型放在 level 或单独的“类型”列，ID 仍按 `{域}{序号}` 编（避免 `K-rep1`、`F-reg` 这类无序号写法）。
7. **跨特性引用**：一律用全称 `FEAT-NNN-{ID}`（`depends_on`、§3.1）。
8. **与代码绑定**：每个场景或测试点 ID 在测试代码中以全称出现（如 `@DisplayName("[FEAT-NNN-ID] …")` 或等价注解），CI 做双向对账。
9. **格式正则**（供 CI）：`^FEAT-\d{3}-[A-Z]\d+(-[a-z][a-z0-9]*)?(\.\d+)?$`（变体在前、测试点在后，与 D1 §6c 一致。2026-11-17 更正：最初写成测试点在前，已发到 PR 548 的评论里仍是错的写法）。
10. **存量处理**：已合入或已被代码引用的 ID 不改名，在“已撤销 ID”表旁登记为“历史写法”及其含义；新规则只约束新增 ID。

FEAT-112 若采用上述规则：现有 ID 保持不变（PR 549 中 84 个 ID 已与测试代码、指纹绑定），在 §5 补“历史写法”说明（`D1a`、`G5a`–`G5c`、`A5.1`–`A5.3`、`E4.1`、`E5.1`–`E5.6`、`K-rep1`–`K-rep3`、`F-reg` 各属哪一级）和“已撤销 ID”表（E5 等），之后新增按新规则编号。
