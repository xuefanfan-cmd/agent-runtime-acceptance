# Python Agent Runtime 文档工程 · AI Coding 指南

本文件是文档维护规范。修改 `docs/` 前先读完；它约束文档内容、示例边界、事实源与导航，不改变 runtime 的代码行为。

## 目标读者与文档定位

本工程同时服务三类读者：

1. **AI 编码助手**：读完一页后，能依据真实签名完成 agent-core 语义开发、runtime 装配与验证。
2. **人类开发者**：理解 agent-core、runtime、适配器与宿主的模块边界、能力范围、运行前置与已知限制。
3. **Runtime 维护者**：能区分 Agent 语义问题、适配器问题、协议问题与部署问题。

## 关键规则（Critical rules）

1. **当前 runtime 与已安装的 agent-core 是事实源。** 类名、函数签名、配置键、事件名、错误码与字段形态必须回到源码、已安装包或测试核实。**源码仓的开发分支不是判据**——agent-core 的 develop 与已安装的 `0.1.16` 存在签名漂移，涉及签名的结论一律以已安装版本上的实测为准。
2. **agent-core 优先。** 新业务 Agent 的语义能力优先使用 `openjiuwen`；runtime 负责托管与服务化。直接实现 `AgentHandler` 只适用于异构框架、远端协议或 runtime 验收替身，并必须标注场景。
3. **文档自包含。** 用户页不能要求读者去看隐藏源码才能完成主流程；正文只引用仓内公开路径与本目录页面。
4. **完整源码与片段分工。** `examples/` 下的类型目录是完整能力闭环（唯一源码来源）；`snippets/` 是可叠加的单文件片段。同一份代码不得在两处各存一份。
5. **中文正文、英文代码。** 术语、章节与解释用简体中文；代码、配置键、HTTP 字段与 Python 符号保留原文。
6. **页面带元数据。** 内容 Markdown 采用 `title`、`description`、`audience`；how-to 另加 `status`，引用示例或片段时加 `examples` / `snippets`。
7. **一项能力一份事实源。** 版本在 `compatibility.md`，agent-core 接口在 `api/agent-core-python.md`，runtime 公开面在 `api/agent-runtime-python.md` 与 `api/runtime-ext.md`，任务路径在 `how-to/`，可复制源码在 `examples/`，原理与边界在 `architecture/` 与 `conventions/`。
8. **改导航同步改索引。** 新页面必须同时更新 `docs/README.md` 与所在目录的 `overview.md`。
9. **证据先于结论。** 「已支持」至少要说明实现、装配与验证等级；「已通过」必须对应实际命令与结果。
10. **不把内部组件当公开 API。** 只在 API 页写宿主或适配器开发者真正需要 import 的对象；内部翻译器、私有 helper 与测试替身不进用户页。
11. **不复制 runtime 源码。** 验收工程可以引用 runtime，但不把 `agent_runtime/` 复制进本仓。
12. **新写的 Markdown 不用符号图标。** 状态用文字表达（已核验 / 未核验、已实现 / 部分实现 / 未实现），不用对勾、叉号与警示符号。

## 导航地图

- **`conventions/`**：`project-conventions.md` 是红线（违反即错）；`openjiuwen开发指导.md` 是按能力分章的正确与错误对照。
- **`architecture/`**：`00` 只讲总体定位、分层与主调用链并给出子文档索引；`01`~`05` 分别是生命周期与状态、协议与兼容、agent-core 架构、协作与扩展、关键机制。
- **`api/`**：一库一文件。`agent-core-python.md`（语义层）、`agent-runtime-python.md`（托管层）、`runtime-ext.md`（适配器与扩展归属）。
- **`how-to/`**：先按 Agent 类型分入口（react / workflow / deepagent / versatile），再是跨类型能力，最后是环境、部署与交付。
- **`examples/`**：一个目录一个能力闭环（完整源码 + 资源 + 装配门禁），另有索引、目录约定与共享最小构建模板。
- **`snippets/`**：单文件增量，索引给出「目标文件名」与「引用它的页面」两列。

## 页面模板

how-to 页正文固定八节，顺序不变：

```text
# <标题：用 X 完成 Y>

## 适用场景 / 不适用场景     ← 帮 AI 做选型判断（如 Workflow 还是 ReAct）
## 最小完整示例              ← 引用 examples/ 工程；机制页可改名「最小装配契约」并引用 snippets/
## 能力点逐个展开            ← 每个能力点一小节：接口 + 最小片段 + 要点
## 配置项参考                ← 粗体定义列表：- **key**：含义。默认值。注意事项。
## 坑位与排错                ← 「注意：」醒目段 + 正确与错误对照 + 现象到检查项的表
## 端到端校验                ← 怎么确认写对了：命令、请求样例、预期结果要点
## API 锚点                  ← 本文涉及的公开符号全限定名（只列用户会直接用的）
## See also                  ← 只列本工程内的相关页面
```

架构页用「一、二、三」中文序号分章；API 页按模块分节并以「API 锚点」收尾。

## 代码示例规范

1. **必须是真实且可运行的代码**：Python 含完整 import 与函数或类声明，禁止「略」「# ...」式省略。
2. **示例演示框架能力而非业务**：一个目录一个能力闭环，命名中性化。
3. **完整代码只有一份**：正文只摘录关键接线，完整源码以 `examples/` 下的类型目录为唯一来源。
4. **版本一致**：示例用到的接口与依赖必须与 `compatibility.md` 的基线一致，不按其他版本的示例推断签名。
5. **装配门禁可跑**：新增或修改 `examples/` 下的工程后，必须跑通该工程的 `tests/`，不需要模型凭据。

## 独立性原则（自包含与可见性）

每一页应当自包含到「读完能动手」的程度：需要的接口签名、配置键与失败形态就写在页内，不靠读者跳三层链接去拼。跨页引用只用于**避免重复事实**（版本、公开签名、能力闭环源码），不用于转移本页该讲清楚的内容。

## 仓库边界（Repository boundary）

本仓是**给开发者与其 AI harness 用的知识源**，不是交付台账。只保留构建 Agent 所需的知识：规范、架构、契约、任务路径、可复制源码、可叠加片段、版本基线。

不进本仓：决策记录与裁定史、审计与对照过程、验收报告与历史验证工程、会话计划与临时笔记。这类内容即使真实也属过程信息，读者不需要它来写代码，留着只会让人分不清哪些是必须遵守的事实。

## 外部改动评审清单（Review checklist）

改动进来时逐条核对：

1. 事实是否有锚点？涉及签名的结论是否在**已安装版本**上实测过？
2. 是否新增了第二份事实源（同一件事在两页各写一遍）？
3. how-to 页是否齐八节？frontmatter 是否完整？
4. 新增示例是否在 `examples/` 下、是否有装配门禁、门禁是否不依赖模型凭据？
5. 新增片段是否被至少一页引用？命名是否是 `<能力>-<工件>.<扩展名>`？索引两列是否补上？
6. 导航是否同步（`docs/README.md` 与所在目录 `overview.md`）？
7. 是否引入了符号图标、是否出现了未验证的能力宣称？
8. 内部链接是否可解析？

## 维护流程

1. 先在已安装包或源码上核实签名与行为，不凭印象改。
2. 更新事实源页面（api / architecture / how-to / examples）。
3. 更新导航与交叉链接。
4. 执行链接检查、模板合规检查与相关装配门禁。
5. runtime 不承载的能力，就地在相关页写明边界，不用模糊措辞掩盖，也不另建缺口台账。
