针对 r2 模板（头提交 `7af5d5ca`）的评审意见。总体认同方向：只做特性验收 SIT、可观测面限于契约/日志/数据、三面都观测不到时提可观测 issue 而不是降级为“由 UT 承接”或以 NOT_OBSERVED 兜底、`depends_on` 与事实来源双向一致、frontmatter 不放评审轮次——这些与 FEAT-112 testplan 修订中的结论一致。建议按下面几点修改后再合入。

## 一、判定态定义与 D1 §9b 不一致（建议优先改）

1. **UNSUPPORTED**：现写“环境/依赖不具备（凭据缺、OS/JDK 不符、上游 bug 阻塞）”。D1 §9b 中 UNSUPPORTED 指“契约可选能力未声明”（与 `required_capabilities` 配合）。把环境缺失归为 UNSUPPORTED，会让缺环境变成合法跳过：例如需要 Docker 或 Linux 的场景在不具备条件的机器上显示 UNSUPPORTED，而不是失败。建议：环境或依赖缺失记 FAIL（原因码如 `infra_failure` / `blocked`），UNSUPPORTED 只用于契约可选能力未声明。
2. **WARN**：现写“判据过线但语义被遮蔽，需人工裁定”。D1 §9b 与现有 testplan 中 WARN 为 SHOULD/MAY 级违反，建议对齐。
3. **EXCLUDED**：示例“并发专项归后续”等于允许推迟 MUST，与 §6“每一条 MUST 都要在 testplan 中被覆盖”冲突。建议 EXCLUDED 只用于 `level=OUT`（非本特性范围）。
4. **原因码**：模板只定义判定态，没有原因码（D1 §9b 的 `must_violation`、`infra_failure`、`conditional_not_triggered` 等）。“前置/激活未成立”现有 testplan 记 FAIL/`conditional_not_triggered`（结论无效、修前置重跑），模板则把“概率事件未激活”放进 NOT_OBSERVED，两边会各写一套。建议补原因码表，并写明“激活未成立”归哪一态。

## 二、事实来源（§4.1）

1. **补“预期只来自特性设计文档”**：L2 与代码只用于定位观测点、构造前置、说明实现事实，不作为期望来源；与特性设计文档冲突时以特性设计文档为准，差异另行提出。FEAT-112 testplan 修订时发现的主要问题（诊断面认证、上下文超长与护栏拦截的探针结果、既有校验错误的写法等），都是把 L2 或实现行为写成了期望。
2. **“特性设计文档（L1 FRS）”**：docs 仓中 FRS 位于 `develop/01-scenarios`，特性设计文档位于 `develop/02-features`，建议分开写：场景需求 FRS（如有）+ 特性设计文档 FEAT（L1）。
3. **版本锚**：建议每类来源都写版本锚（commit），不只限于被依赖特性的 testplan。
4. **双向一致的例外**：被依赖特性的 testplan 可能尚未合入（目前 FEAT-111 testplan 仍在 PR 514），此时给不出路径与 commit。建议允许写“testplan 未合入”，`depends_on` 保持 FEAT 级，合入后补齐。

## 三、可观测三面与兜底（§4.2）

1. **优先级**：建议写明先契约、再日志、再数据。用作判据的日志行或表字段建议在 L2 中声明，否则实现一改即误判；“strong-eq 行数断言”作为示例偏脆，可改为“固定事件名/错误码出现与否”。
2. **触发条件**：“L2 定义的 MUST”建议改为“特性设计文档或 L2 定义的 MUST”。
3. **可构造性**：除“观测不到”外，还有“前置构造不出来”的情况（如需要过期的终态事实、需要某类部署宿主）。建议写明：先用测试侧环境手段（时钟控制、测试托管的数据面、依赖故障注入等）构造，仍不行同样提 issue。

## 四、结构与措辞

1. **编号撞号**：新增的 4.1/4.2/4.3 位于模板 §4“章节骨架”下，和紧邻代码块中 testplan 自身的 §4.1 整体拓扑、§4.2 外部依赖、§4.3 Fixture 清单重号，“走 §4.2 的兜底原则”难以判断指哪一处。建议单独成章（如“## 5. 正文硬约束”），后续章节顺延。
2. **`docs/review/` 路径**：docs 仓顶层只有 `develop/`、`guides/`，没有该目录，§4.1 与 §6 都引用了它，需指定实际位置。
3. **正文禁入的写法**：按关键词禁 `demo`、`UT` 过宽——§4 部署拓扑本来就要描述被测载体与替身，“开发侧单测仅供参考、不计入验收”这类说明也会提到 UT。建议按语义禁止：不得以载体就绪状态或 UT 覆盖作为不覆盖某条 MUST 的理由。
4. **Fixture 三处**：骨架中 §4.3 Fixture 清单、§7 Fixture、附录 B Fixture 库索引职责重叠，可顺带收敛为一处。
5. **PR 说明**：说明仍写“6 态 → 三态”“删 `required_capabilities`”，这两处已在后续提交中回退，建议更新说明。

## 五、建议新增：ID 与测试点编号规则

模板目前只在“与 D1 洞察的对应”表中引用格式 `FEAT-NNN-{domain}{seq}[-{variant}][.{point}]`，没有规定各段含义及新增、拆分、撤销时如何编号。FEAT-112 testplan 已出现不一致写法：`D1a`、`G5a` 用字母后缀；`A5.1`–`A5.3` 实为同一期望的不同输入；`E5.1`–`E5.6` 实为前置与步骤都不同的独立场景；`B1.1`–`B1.3` 才是同一场景下的检查点；`K-rep1`、`F-reg` 没有序号。建议新增一节：

1. **三级结构**：场景 `FEAT-NNN-{域}{序号}`（§5 一行）；测试点 `{场景}.{n}`（同一前置与步骤下需分别给出结论的检查，场景结论取各测试点中最严重的）；变体 `{场景}-{变体}`（同一期望、不同输入或部署形态，变体名用小写短词，如 `-run`、`-stream`、`-open`、`-half`）。
2. **定级**：前置或步骤不同 → 新场景（新序号）；前置与步骤相同、检查项不同 → 测试点；期望相同、输入不同 → 变体。
3. **域**：每个 testplan 在 §5 开头列出域字母及含义；新增域按字母顺序追加，已用字母不改含义。
4. **序号**：从 1 开始按新增顺序递增，不按表内位置、不重排，允许空号；插入新场景不借用 `.n`。
5. **撤销与拆分**：撤销的 ID 永不复用，在 §5 末尾“已撤销 ID”表登记“原 ID → 原因 → 替代 ID”。
6. **类型不进 ID**：代表场景、回归冒烟等类型放在 level 或单独的类型列，ID 仍按 `{域}{序号}` 编。
7. **跨特性引用与代码绑定**：一律用全称 `FEAT-NNN-{ID}`；每个场景/测试点 ID 在测试代码中以全称出现，CI 双向对账。格式正则供参考：`^FEAT-\d{3}-[A-Z]\d+(\.\d+)?(-[a-z][a-z0-9]*)?$`。
8. **存量处理**：已合入或已被代码引用的 ID 不改名，登记为“历史写法”并注明属于哪一级；新规则只约束新增 ID。
