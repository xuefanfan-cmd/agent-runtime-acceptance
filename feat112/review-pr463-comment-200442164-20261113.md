# PR 463 评审评论（200442164）可行性评估

日期：2026-11-13。评论：`weixin_45837958`，2026-11-13 09:25，仅针对 FEAT-112《任务终态结构化分类规格》（ext L2）。PR 头提交仍为 `8039074e`，评论后无新提交。

评估口径：以特性档 `05af9cc3` 为锚点；对照代码（solution `ec105dfb9`、agent-core-java develop `0db55c68e`）与差异清单（docsReview `08d9dc4`）。

## 总体结论

**可以按评论修改，但不能止于评论。** 评论的方向是“规格先如实描述现行实现，再保留真实差距”，这比现在把启发式写成已满足要好，所列事实也都与代码相符。但有三处如果照评论原样落笔，会把与特性档不一致的实现固化为设计，需要改写措辞或补充：

1. **§6 探针健康范围**：评论要求写“四类均可关门”，并注“特性档需补齐这一范围”。这等于预设特性档向实现看齐。应改为“当前实现四类关门；INPUT_REJECTED、GUARDRAIL_DENIED 是否属于健康结果待特性设计裁决，若裁定不属于，实现需改”。尤其 GUARDRAIL_DENIED：DA 中它只会产生于“拒绝后原因不明的失败”，把它当健康证据，意味着一个原因不明（可能是系统故障）的探针失败也能宣告恢复。
2. **181012 识别**：评论要求“如实写明跨模块模板契约及措辞变化风险”。但 core 0.1.17 已在错误结果里提供结构化 `failure`（`numericCode=181012`），是 DA 翻译时丢弃了（`DaEventTranslator.java:572-574`）。把文本模板写成“契约”会固化一个绕路做法，与特性档第 260 行和 FEAT-054 第 243 行不符。应写成以 core 结构化 `failure` 为来源的目标行为，当前匹配文本是待修复的实现缺陷。（2026-11-16 更正：此前写“规格写成‘当前实现匹配文本，属差距’”不对——规格是锚点，写目标，不描述实现现状。）
3. **护栏因果**：评论要求如实写成启发式并保留差距，可以。但差距需要有裁决与责任方，不能只是“记录在案”：core、DA、FEAT-109 三方都不会因拒绝终止任务，该分支只豁免特性档 §6 明确禁止豁免的情形（差异清单第六条）。
