# FEAT-112 D1a 判据样板：OPEN 时拒绝新任务

本文件是 cases md 的评审样板，不是已实现的测试配置或测试报告。仅整理 D1a，并说明它与 D3、D6 的关系；尚未开发判据执行器、采集器或自动化用例。

## 1. 在端到端流程中的位置

特性档定义要求 → testplan 分配场景 ID → cases 写清前置、取证与判据 → 测试驱动真实 demo 并留证 → 判据检查证据 → 用正确和错误样本检查判据自身 → 将验证结果反馈到 D1/D2。

本样板处于第三步。solution 基线为 `0.1.4`；它不是判据自身的修订号。未来执行报告还需记录特性档/testplan 的 commit、测试代码版本、demo 构建版本和配置，不能只凭一个版本号追溯。

## 2. 判据依据与边界

本次核对的是本地 docs 仓快照，未声称已核对远端最新内容：

- [特性档 §3.1](.src-cache/docs-repo/develop/02-features/FEAT-112-task-degradation-gate.md)：双入口拒收 JSON 示例及字段/行为契约表。
- [testplan §5.4](FEAT-112-task-degradation-gate-testplan.md)：D1a 响应内容、D3 恢复时间一致、D6 拒收零副作用。
- 实现定位 `DaEngineDegradedException` 构造器及 `DaCompatController.engineDegraded` 仅用于核查当前行为，不代替需求规定。

核对结论：

1. 特性档 §3.1 明确：`code` 固定为 `ENGINE_DEGRADED`，不复用 `ENGINE_BUSY` 或 `ENGINE_INTERNAL`。
2. testplan D1a 写的是 body **含**所列字段；特性档没有规定字段集合封闭。因此本样板检查必需字段，不因出现额外 `requestId` 就判失败；这不等于宣称任意扩展都合规。
3. `error` 精确文案在 testplan D1a 中明确，特性档 JSON 示例也给出相同文案；字面比对依据是这份基线，而不只是代码中写死了字符串。
4. `/api/agents/run` 的这份拒收体是 DA HTTP 接口契约，不应套用 A2A JSON-RPC 响应 schema。真正的 A2A 报文应引用与 SUT 协议版本匹配的官方 schema；HTTP 头、诊断面和本接口仍需各自的定义。
5. HALF_OPEN 探针占用属于另一场景，不塞进 D1a 的条件分支。

旧样板的 `J-D1a-9`（严格 7 字段白名单）撤回，不作为门禁；旧的 `§X.Y` 引文和猜测的文档锚点一并撤回。下表使用带 FEAT 前缀的候选 ID，原短 ID 仅是草稿别名，未接入代码。

## 3. 怎么执行、拿什么证据

### 前置

- 使用真实 DA demo，配置启用降级门；请求认证、参数、媒体和 team 均满足入口要求，避免先被其他校验拒绝。
- 通过 LLM stub 注入故障和真实任务执行使门进入 OPEN，不使用强制改门状态的测试接口。
- 在同一实例上记录 OPEN 诊断快照，配置足够的静默期余量，避免请求到达前转入 HALF_OPEN；停止额外故障注入和无关并发请求。
- OPEN 激活证据是前置证据，不能只用被测响应中的 `state=OPEN` 自证前置成立。

### 操作

向同一实例 `POST /api/agents/run` 提交一条合法新任务。记录请求开始/结束时间、请求关联标识、HTTP 状态、响应头和 JSON 响应体。

### 留证边界

记录前置诊断与目标请求的关联关系、实例、配置、时间以及采集是否完整。认证头和密钥必须脱敏，不能因使用 stub 就认为轨迹无敏感信息。

离线判据只读取这些已采集证据，不重新调用 SUT。证据没有记录的事实不能事后推算成已验证；前置未建立、记录缺失与明确契约违规分别报告，不能都显示 PASS。

## 4. 给评审人看的判据清单

以下均为候选自动化判据，尚未运行验证。预期值由场景基线决定，不根据被测响应自行改变预期。

| 判据 ID | 检查什么 | 期望 | 依据/归属 |
|---|---|---|---|
| FEAT-112-D1a-J01 | HTTP 状态 | 503 | 特性档 §3.1；D1a |
| FEAT-112-D1a-J02 | `body.error` | `Agent is temporarily not accepting new tasks` | testplan D1a；特性档 §3.1 示例 |
| FEAT-112-D1a-J03 | `body.code` | `ENGINE_DEGRADED` | 特性档 §3.1 字段表；D1a |
| FEAT-112-D1a-J04 | `body.degraded` | 布尔值 true，不是字符串 | 特性档 §2 验收出口 7；D1a |
| FEAT-112-D1a-J05 | `body.retryable` | 布尔值 true | 同上 |
| FEAT-112-D1a-J06 | `body.state` | OPEN | D1a 已建立的前置 |
| FEAT-112-D1a-J07 | `body.instanceId` | 非空，且与目标实例的诊断证据一致 | 特性档 §3.1 实际拒收实例 |
| FEAT-112-D1a-J08 | `body.retryAfterSeconds` | 存在，JSON 整数且非负 | 特性档 §3.1 剩余秒数；不据此声称已证明取整算法 |
| FEAT-112-D1a-J10 | `Retry-After` 与响应体 | 同一次拒收响应中，头为十进制秒数，与 body 值相同 | 复用 D3 的一致性要求，不另造一个场景 |
| FEAT-112-D1a-J11 | 响应格式 | 可解析的 JSON 对象；媒体类型为 application/json，允许合法 charset 参数 | 特性档 §3.1 JSON 响应形态 |

不检查 JSON 字段顺序；不将额外普通字段一律判为错误。敏感数据泄露需要独立且明确的契约依据，不能用“字段只能有 7 个”替代安全判据。

`retryAfterSeconds` 是返回的整数秒数。精确向上取整边界可由受控时间的机制测试验证；SIT 可检查公开面的同值、范围及状态转换，但不能把“头体相等”说成完整的算法证明，也不能据此推导复杂判据不可数据化。

## 5. 响应合格不等于端到端合格

D1a 通过只能证明拒收响应符合上述要求。还需沿 testplan 继续验证：

| 场景 | 额外证据 | 不能偷换成什么 |
|---|---|---|
| D1b 流式入口拒收 | SSE 建立前的 HTTP 响应、是否出现任务事件 | 不能用 /run 的结果代表 /run-stream |
| D6 拒收零副作用 | 前后任务列表、窗口快照、stub 调用记录等，并排除无关并发及窗口过期干扰 | 不能仅凭收到 503 就声称没有创建任务或调用模型 |
| HALF_OPEN 拒收 | 独立探针占用前置、该次拒收响应 | 不能用 OPEN 的字段集验证 HALF_OPEN |

stub 无新增调用只是“模型未调用”的证据，不单独证明内部执行许可未创建。公开证据无法证明的内部事实应标明边界并由相应层级测试承接。

## 6. 怎么证明判据既能抓错、又不误报

先构造离线响应证据样本，不必为每条规则启动一个假 SUT，也不预先引入 HTTP 代理。下列是待实现的判据自测设计，不是已通过的测试结果。

| 样本 | 在正确基线上改什么 | 预期 |
|---|---|---|
| 正确基线 | 必需字段及头体一致 | 所有本样板判据通过 |
| 错误错误码 | `code` 改为 `ENGINE_BUSY` | J03 失败 |
| 缺字段 | 删除 `code` | J03 失败，报告缺失而非字符串不相等 |
| 类型错误 | `degraded` 改为字符串 `"true"` | J04 失败 |
| 头体矛盾 | body 为 10，Retry-After 为 9 | J10 失败 |
| 普通扩展字段 | 增加 `requestId`，其余不变 | 本样板不因多字段而失败，不代表已证明全部扩展语义合规 |
| 等价表示 | 调整 JSON 键顺序、Content-Type 加合法 charset | 不误报 |
| 缺前置证据 | 删除 OPEN 激活记录 | 不能给出场景 PASS；报告前置证据不足 |

失败报告至少包含：场景 ID、判据 ID、期望/实际、前置、证据记录位置及基线引用。例如：

```text
场景 FEAT-112-D1a / 判据 FEAT-112-D1a-J03
前置：目标实例已通过独立诊断记录确认 OPEN
期望：body.code = ENGINE_DEGRADED
实际：body.code = ENGINE_BUSY
依据：特性档 §3.1 code 字段；testplan §5.4 D1a
证据：本次运行目标请求的响应体 $.code
```

## 7. 对 D1/D2 的反馈：结论与待验证设想分开

| 维度 | 本轮已核对的认识 | 后续如何验证/刷新 |
|---|---|---|
| D1 契约依据 | 实现列出 7 个字段不能推出契约禁止额外字段 | 洞察区分“需求依据”和“实现证据”；本例撤销无依据白名单 |
| D1 关联 | D1a、D3、D6 分别承接响应、恢复时间与副作用 | cases/代码引用原场景 ID，避免重复分配或把响应通过夸成全链路通过 |
| D2 判据独立 | 固定格式有利于采集和字段检查，但 DA HTTP 不是 A2A JSON-RPC | 先区分证据种类，再验证判据是否能离线消费；不先建设通用 DSL |
| D2 判据分类 | “检查什么”与“证据来自哪里”不是同一维度 | 本例检查外部契约、证据来自 HTTP；DB/Redis 是证据源，日志通常为诊断，也可能承载明确的日志契约。完整分类待其他场景验证 |
| D2 判据自测 | 抓错与不误报都重要，样本可直接作用于判据输入 | 实现 §6 自测后再报告通过情况，不把写出样例称为 red-first 已落地 |
| D2 证据边界 | 证据不足限制的是能证明什么，不等于判据无法数据化 | 留证后才能验证重评；无需为重评复制 SUT 内部状态机 |

本轮只改评审样板；没有更新 PPT、正式 testplan 或代码，没有提交或发布 PR。下一阶段需实现最小采集与判据自测，拿实际结果验证这份样板，再决定扩展到其他场景及刷新洞察材料。
