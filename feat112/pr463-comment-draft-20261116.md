针对上一条评审结论（评论 200480678）的补充，只涉及本 PR 中的 ext L2《任务终态结构化分类规格》（DA L2 的修改另行跟进，不在本 PR 体现）。

我们按 FEAT-112 特性档（05af9cc3）、solution `6bf40476c` 与 agent-core-java develop `0db55c68e` 逐条核对了上一条评论，认同其全部修改意见，可以按其修改。以下三处上一条评论没有覆盖，建议在同一轮一并修改：

**1. §2、§3 仍把建档前返回的请求写成 NOT_ADMITTED**

§2 第 45 行 NOT_ADMITTED 的来源列着“入站认证/参数/媒体 4xx……降级门自身拒收”，§3 第 63–64 行把这两类映射为 NOT_ADMITTED。按上一条评论第一节第 2 项，这些请求在任务建档前返回，不产生终态事实；认领探针后因待答任务数触顶返回 `ENGINE_BUSY` 的请求同样在建档前返回。§2、§3 若不同步修改，§3 的“覆盖性自检”会与 §4 自相矛盾。

建议：这几类写为“不产生事实、不计入窗口”；NOT_ADMITTED 只保留已建档、实际落定的无结论结果（`session_busy`、`pool_saturated`，以及分类待裁决的 `prepare_failed`）。记账结论不变。

**2. §8 第 ② 问在修改后不再成立**

§8 请需求侧确认“§1 因果证据语义与裁定是否一字不差”。按上一条评论修改后，§5 不再把“无系统异常证据”等同于最终因果闭合，护栏因果改为待裁决项。建议改写 §8：不再请求确认“一字不差”，改为请需求侧裁决上一条评论第三节的三项。

**3. §5 应写明 core 结果轮 error 通道涵盖哪些终态**

§5 第 100、106 行把该通道写作“模型重试耗尽等”，范围不清。走这条通道的终态还包括：
- 运行中止（completion_timeout、core 侧中断的轮次）：属于特性档 §5.1.3 第 252 行“连接/流/任务超时”，计入分子；
- core 达到最大迭代次数（“Max iterations reached without completion”）：没有结构化类别的未知失败，按特性档 §5.1.3 第 258 行按系统异常记账，计入分子。

建议 §5 逐项写明该通道涵盖的终态及其分类依据。

另有两条建议：

- **结构化码的范围。** 上一条评论第二节以 181012 为例。目前同样靠错误文本识别的还有 181008 超时、181009 限流、181010 配额、181011 认证（DaErrorCodes 第 64–68 行），建议规格把五个码统一写为由 core 结构化 `failure` 的 `numericCode`/`code` 派生。对 FEAT-112 的记账，只有 181012 会改变是否计入分子；其余四个都计入分子。
- **裁决顺序。** 上一条评论第三节第 1 项（护栏最终因果）宜先于第 3 项（INPUT_REJECTED/GUARDRAIL_DENIED 的探针健康口径）裁决：若去掉“无系统异常证据即闭合”分支，GUARDRAIL_DENIED 在 DA 中不再有产生路径，第 3 项中关于它的部分会随之变化。
